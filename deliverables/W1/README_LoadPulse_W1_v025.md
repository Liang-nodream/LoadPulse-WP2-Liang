## 本週確立的設計方向

### 1. 模型不是只比誰的 RMSE 最低

研究將逐層增加可使用的資訊，觀察新資訊能否降低負載預測誤差：

| 階層 | 候選資訊集合 | 要回答的問題 |
|---|---|---|
| **M0** | 小時、星期、月份 | 純時間／日曆規律能解釋多少？ |
| **M1** | M0 + 時間趨勢 | 長期趨勢是否提供額外解釋？ |
| **M2** | M1 + 分層假日 | 假日資訊是否改善預測？ |
| **M3** | M2 + 氣象主效應 | 氣象資訊是否改善預測？ |
| **M3+** | M3 + 氣象交互作用 | 氣象效果是否隨時間、季節改變？ |

另外規劃 **M_AR**（加入「預測時點已可取得」的歷史負載）作為旁支參照，以及 **seasonal-naive** 作為獨立基準。Ridge／GAM 是模型形式的候選比較，須控制所使用的資訊集合，不能把「多了資訊」誤當成「模型方法比較好」。

### 2. 公平比較的前提：完全相同的預測條件

- 使用相同的區域負載定義、時間基準、目標時段、預測發布時點及預測時距。
- **候選**發布規則：在目標日前一天當地 **12:00** 產生次日逐時預測；正式設定仍待確認。
- 依時間順序區分 **Development → Calibration → Confirmation**，不隨機打亂，不使用未來資料調參。
- 規劃 **rolling-origin** 樣本外評估；所有歷史負載、預報天氣與訓練標籤都必須在對應 origin 前實際可取得。
- **實際天氣**的回顧性分析與**歷史天氣預報**的可部署分析必須分開，不能混報。

### 3. 預測輸出先統一格式，才能比較模型誤差

每筆預測至少需能追溯：`timestamp`、`origin_time`、`horizon`、`split`、`model_id`、`model_version`、`actual`、`prediction`、`residual`、`loss`、`quality_flag`；另規劃 `run_id`、`region_id`、`data_version` 等欄位。

- 以同一個 **run／區域／資料版本／資訊模式／切分／目標時間／預測時點／時距** 配對不同模型。
- 缺值或品質不合格的時段**保留記錄並標記無效**，不能先各自刪除再比較。
- 配對損失候選定義：`delta_loss = loss_reference - loss_candidate`；正值表示候選模型的絕對誤差較小。
- `prediction_schema.md` 的 CSV 僅為 **mock 格式示例**，不是已產出的實驗結果。
